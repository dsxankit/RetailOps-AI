# RetailOps AI

**Local AI-powered SOP assistance, incident routing, and operational analytics for retail stores.**

RetailOps AI is a Streamlit application that helps store employees look up operating procedures, report incidents, and track their resolution. It combines a locally hosted language model for policy questions with deterministic Python rules for operational routing, SQLite for ticket management, and Pandas for reporting.

> **Independent portfolio project:** RetailOps AI is not an official V-Mart product or authorized internal system. The SOP documents and example incidents are synthetic and intended for demonstration only. Responses should not be treated as verified company policy.

## Features

### SOP assistant

- Uses `qwen3:4b-instruct` through Ollama for local inference.
- Loads sample SOPs from `sops/*.md`.
- Answers policy questions with supporting filenames and sections.
- Responds out of scope when a question is not covered by the available SOPs.

Source references are generated by the model and are not independently verified. The application uses full-context prompting rather than vector-search retrieval-augmented generation (RAG).

### Incident classification and routing

- Uses deterministic keyword and regular-expression rules in `routing.py`.
- Supports multiple applicable rules for one incident.
- Preserves SOP-defined escalation and approval responsibilities.
- Sends unmatched or ambiguous cases for manual review.
- Does not automatically authorize refunds, price overrides, or inventory adjustments.

### Ticket management

- Requires explicit confirmation before creating a ticket.
- Stores the incident, classification, assigned role, actions, and SOP references in SQLite.
- Supports **Open**, **In Progress**, and **Resolved** statuses.
- Displays tickets and allows manual status updates.

### Analytics

- Shows ticket totals by status.
- Calculates resolution rates and manual-review counts.
- Displays ticket distributions by category and status.
- Includes a scenario-based time-savings estimator. Its results are projections, not measured pilot results.

## Architecture

```text
Streamlit interface (app.py)
├── SOP assistant
│   └── ai.py + sops/ -> Ollama / Qwen3
├── Issue reporting
│   └── routing.py -> review and confirmation
└── Analytics dashboard
    └── analytics.py -> Pandas aggregations

database.py -> SQLite tickets
             data/retailops.db
```

The language model generates policy explanations, Python rules determine incident routing, and the user authorizes ticket creation.

## Getting started

### Prerequisites

- Python and [`uv`](https://docs.astral.sh/uv/)
- [Ollama](https://ollama.com/) installed and running locally
- Enough system resources to run `qwen3:4b-instruct`

### Install and run

```bash
git clone https://github.com/dsxankit/RetailOps-AI.git
cd RetailOps-AI
uv sync
ollama pull qwen3:4b-instruct
uv run streamlit run app.py
```

If Ollama is not already running, start it separately:

```bash
ollama serve
```

Open <http://localhost:8501>. The application requires access to the local Ollama service; deploying Streamlit separately does not make the model available on the deployment server.

## Supported incident rules

| Rule | Issue | Routing / handling | SOP |
|---|---|---|---|
| `RETURN_NO_RECEIPT` | Return without a receipt | Escalate to Store Manager | `returns.md`, Section 1 |
| `RETURN_MISSING_TAGS` | Missing original tags | Manual review; no automatic exception approval | `returns.md`, Section 1 |
| `DAMAGED_IN_STORE_RETURN` | Damaged in-store return | Inspection and Store Manager approval | `returns.md`, Section 3 |
| `BILLING_PRICE_MISMATCH` | Shelf/POS price mismatch | Floor Supervisor verification and authorization | `billing.md`, Section 3 |
| `SHIPMENT_DISCREPANCY` | Shipment/ASN discrepancy | Receiving Associate logs issue; Store Manager signs | `inventory.md`, Section 1 |
| Fallback | No matching rule | Unclassified; manual review | Not applicable |
| Cross-department match | Rules from different departments | Flag for review | Applicable SOPs |

A description can match multiple rules. Because classification uses keywords and regular expressions, phrasing matters; unrecognized descriptions may require manual review.

## Ticket workflow

1. An employee reports an operational issue.
2. Python evaluates the description against routing rules.
3. The interface displays the category, action, role, and SOP reference.
4. The employee selects **Create Ticket**.
5. The ticket is saved with status **Open**.
6. A user updates it to **In Progress** or **Resolved**.

```text
Open -> In Progress -> Resolved
```

The database restricts status values but does not enforce transition order or verify that a resolution occurred. The prototype has no role-based permissions. Ticket records retain routing actions and references as a snapshot from creation time.

## Analytics

```text
Resolution rate (%) = Resolved tickets / Total tickets * 100
```

An empty database displays a zero state. The time-savings estimator uses user-provided assumptions:

```text
Estimated hours saved per month
  = Monthly SOP queries * max(0, Manual lookup minutes - AI lookup minutes) / 60
```

These are hypothetical estimates, not observed productivity improvements or financial ROI.

## Tests

```bash
uv run python -m unittest discover -s tests -p "test_*.py" -v
```

`tests/test_questions.md` contains manual SOP-answer scenarios. Model responses should be checked for groundedness, correct references, and appropriate abstention after changing models or prompts.

## Limitations

- The project contains only three sample SOP files.
- LLM responses and references are not guaranteed to be accurate.
- Keyword routing may miss unusual or ambiguous phrasing.
- All SOPs are sent in the prompt; larger collections would need retrieval and citation verification.
- There is no authentication, authorization, or immutable status history.
- Time-savings estimates do not use observed pilot timings or operating costs.
- The project is a local prototype, not a production multi-store service.
